# 维护者手册（中文）

这份手册写给项目负责人：别人如何提交建议，你如何审批，以及什么时候内容会真正发布到网站上。

## 一句话说明

**任何人都可以提建议、提交修改；只有你批准并合并后，修改才会进入 `main` 分支；网站只从 `main` 发布。**
所以，没有经过你批准的内容，永远不会出现在线上。

## 别人可以怎么参与

| 方式 | 在哪里 | 需要你做什么 |
|---|---|---|
| 提建议、报问题 | GitHub 的 **Issues**（有“建议 / 问题反馈 / 翻译”三个模板） | 看一看、回复、打标签；采纳的话可以自己改，或者请对方提交修改 |
| 提交修改（代码、文案、翻译、设计） | **Pull Request（PR）** | 审阅后点“批准”并“合并”，或者提出修改意见、或者关闭 |

外部贡献者没有写入权限，他们只能 *fork*（复制一份仓库）后，向你的仓库发起 PR。

## 仓库上开启的保护（建好 GitHub 仓库后由我配置）

对 `main` 分支设置规则（GitHub Rulesets）：

- 禁止直接推送到 `main`，所有修改都必须走 PR；
- 禁止强制推送和删除 `main`；
- PR 必须 **通过自动检查**（翻译完整性、代码检查、类型检查、单元测试、构建）；
- PR 必须 **得到代码负责人（你）的批准**（由 `.github/CODEOWNERS` 指定）；
- 批准之后如果对方又提交了新改动，**需要重新批准**；
- 你作为仓库管理员可以合并自己的 PR（GitHub 不允许自己批准自己），但同样只能通过 PR，不能绕过。

其他设置：

- 外部贡献者的 PR 首次运行自动检查前，需要你点一下“批准运行”（防止有人借检查流程做坏事）；
- 只允许“压缩合并”（Squash merge），让历史记录清楚；合并后自动删除分支。

## 审批一个 PR 的步骤（网页上操作）

1. 打开仓库 → **Pull requests** → 点开要审的 PR。
2. 看 **Files changed**：每一处修改都会标出来。文案修改主要看 `messages/zh-Hans.json` 和 `messages/en.json`。
3. 看底部的自动检查是否全部打勾（绿色 ✔）。如果是外部贡献者第一次提交，需要先点 **Approve and run** 才会开始检查。
4. 决定：
   - 满意 → **Review changes → Approve → Submit review**，然后点 **Squash and merge**；
   - 需要修改 → **Review changes → Request changes**，写下意见；
   - 不采纳 → 留言说明原因后 **Close pull request**。
5. 合并后，网站会自动从 `main` 重新发布（部署配置好之后）。

建议重点检查：

- 是否违反[章程](../CHARTER.md)：把付费作为加入的条件、出售数据、宣称医疗/宗教/法律认证、评判或施压他人（自愿的高级徽章、周边是允许的，但要先公开讨论）；
- 是否加入了统计、广告、第三方脚本，或收集新的个人信息；
- 新增的依赖包（`package.json`）是否必要、是否可信；
- 卡片相关的修改是否附带了导出图片的截图。

## 发布

- 网站只从 `main` 构建和发布。
- 部署平台确定后（推荐 Cloudflare Pages 加自定义域名），可以再加一道“发布审批”：每次发布前在 GitHub 上点一次批准才会上线。

## 以后扩大团队

当某位贡献者长期可靠，可以邀请他成为某个领域（比如某种语言的翻译）的维护者：把他的 GitHub 用户名加到 `.github/CODEOWNERS` 对应的路径，并在 [GOVERNANCE.md](../GOVERNANCE.md) 中记录。
